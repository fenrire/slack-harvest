# 아키텍처 결정 기록 (ADR)

## 핵심 요구사항

- Slack 워크스페이스의 모든 채널 데이터를 로컬에 아카이빙
- 아카이빙된 데이터를 다양한 방식으로 분석 (주제별 취합, 결론 추출, to-do 정리 등)
- **분석 요구사항이 계속 달라질 수 있음** → 유연한 구조가 핵심

---

## ADR-1: 2-레이어 하이브리드 아키텍처

### 결정

SQLite(구조적 저장) + Markdown/QMD(시맨틱 검색) 2-레이어 구조 채택

### 검토한 대안

| 방식 | 장점 | 단점 |
|------|------|------|
| **A. 순수 SQLite** | 구조적 쿼리 강력, 단순 | "A 주제의 결론이 뭐야?" 같은 시맨틱 질의 불가 |
| **B. 순수 Markdown/QMD** | 시맨틱 검색 가능 | "누가 언제 어디서" 구조적 쿼리 어려움, 원본 메타데이터 손실 |
| **C. 하이브리드 (채택)** | 양쪽 장점 모두 활용 | 내보내기 단계 추가 필요 |

### 이유

Slack 데이터는 **구조적이면서 동시에 비정형**이다.

- "이번 달 가장 활발한 사용자는?" → SQL 쿼리로 즉시 답변
- "마이그레이션 관련 결정사항 정리해줘" → 시맨틱 검색 + LLM 분석 필요

하나의 도구로는 양쪽을 모두 커버할 수 없으므로, **SQLite를 원본(source of truth)**으로 두고 **QMD용 Markdown을 파생 뷰**로 생성하는 구조가 최적.

## ADR-2: SQLite 선택 (vs PostgreSQL, MongoDB 등)

### 결정

SQLite를 단일 데이터 저장소로 사용

### 이유

- **서버 불필요**: 파일 하나로 완결, 별도 프로세스 없음
- **Python 내장**: `sqlite3` 모듈이 표준 라이브러리에 포함
- **이식성**: DB 파일을 복사만 하면 백업/이동 가능
- **성능 충분**: 수십만 메시지 규모에서 WAL 모드 + 적절한 인덱스로 충분
- **동시성**: 쓰기는 단일(harvester), 읽기는 다중(exporter, analyzer) → WAL 모드로 해결

PostgreSQL이나 MongoDB는 이 규모에서 과도한 인프라.

## ADR-3: raw_json 컬럼 보존

### 결정

users, channels, messages, files 테이블에 `raw_json TEXT` 컬럼 추가

### 이유

Slack API 응답에는 수십 개의 필드가 있지만, 정규화된 컬럼으로는 그 중 일부만 커버한다. 지금은 필요 없어 보이는 필드가 나중에 분석 요구사항이 바뀔 때 필요해질 수 있다.

- 정규화 컬럼: 일상적인 쿼리의 95%를 커버
- raw_json: 나머지 5%의 탈출구 (스키마 변경 없이 `json_extract()`로 접근)

**데이터를 한번 잃으면 복구 불가** → 저장 비용이 낮으므로 원본 전체를 보존.

## ADR-4: Markdown 월별 파일 그룹핑

### 결정

채널별 디렉토리 안에 `YYYY-MM.md` 월별 파일로 구성

### 검토한 대안

| 단위 | 장점 | 단점 |
|------|------|------|
| 일별 | 작은 파일, 정밀한 증분 | 파일 수 폭증 (365개/년/채널), QMD 인덱싱 비효율 |
| 주별 | 적당한 크기 | 월 경계 처리 애매 |
| **월별 (채택)** | 적당한 파일 수, 자연스러운 단위 | 매우 활발한 채널은 파일이 클 수 있음 |
| 채널 전체 | 파일 수 최소 | 대형 채널에서 수십 MB, LLM 컨텍스트 초과 |

### 이유

- 연간 채널당 12개 파일 → 관리 가능한 수준
- 활발한 채널도 월별 50~100KB 수준 → QMD 인덱싱과 LLM 컨텍스트 모두 적합
- 증분 내보내기 단위로도 자연스러움 (해당 월에 새 메시지가 있으면 재생성)

## ADR-5: Python 선택 (vs TypeScript)

### 결정

Python으로 구현

### 검토한 비교

| 기준 | Python | TypeScript |
|------|--------|------------|
| SQLite | 내장 (`sqlite3`) | 외부 패키지 (`better-sqlite3`) |
| 데이터 분석 | pandas, numpy 생태계 | 약함 |
| LLM 연동 | anthropic SDK, langchain 등 풍부 | 동등 |
| Slack SDK | `slack-sdk` 공식 지원 | `@slack/web-api` 동등 |
| QMD 연동 | MCP로 외부 연동 | 같은 Node.js 생태계, import 가능 |

### 이유

이 프로젝트의 핵심은 **데이터 수집 후 분석**이다. 분석 요구사항이 계속 변하고 복잡해질 수 있으므로, 데이터 처리 생태계가 압도적인 Python이 유리하다.

QMD는 TypeScript로 작성되었지만, MCP 서버로 외부 연동이 가능하므로 Python에서도 QMD 검색을 활용할 수 있다.

## ADR-6: Slack Bot Token API (vs Export ZIP)

### 결정

Slack Bot Token (`xoxb-`) API를 통한 데이터 수집

### 검토한 대안

| 방식 | 장점 | 단점 |
|------|------|------|
| **Bot Token API (채택)** | 스레드 완전 포함, 증분 동기화, 리액션/파일 풍부 | Slack App 생성 필요, 레이트 리밋 |
| Workspace Export ZIP | API 없이 한번에 | Public만, 스레드 불완전, 실시간 불가 |
| User Token API | Private/DM까지 접근 | 보안 위험, 개인 토큰 의존 |

### 이유

- **스레드 데이터가 핵심**: Slack에서 깊이 있는 논의는 대부분 스레드에서 일어남. Export ZIP은 스레드 답글이 불완전
- **증분 동기화**: 한번 전체 수집 후에는 새 메시지만 가져오면 됨 → API가 유일한 방법
- **메타데이터 풍부**: 리액션, 파일 정보 등이 분석에 중요한 신호

## ADR-7: 레이트 리밋 3단계 전략

### 결정

SDK 내장 + 사전 방지(AdaptiveRateLimiter) + 재시도(tenacity) 3단계

### 이유

Slack Tier 3 API는 약 50 req/min 제한이 있다. 단순히 429 에러 후 재시도만 하면:
- 불필요한 실패/재시도 사이클 발생
- 연속 429로 더 긴 대기 시간 부과 가능

**사전 방지(1.3초 간격) + 적응적 조절**로 429 자체를 최소화하고, 발생 시 SDK와 tenacity가 안전하게 재시도.

## ADR-8: 스레드 인라인 렌더링

### 결정

Markdown에서 스레드를 부모 메시지 아래 blockquote(`>`)로 인라인 렌더링

### 검토한 대안

1. **별도 파일로 분리**: 스레드마다 파일 생성 → 파일 수 폭증, 맥락 단절
2. **답글만 시간순으로 섞기**: 채널 타임라인에 답글 삽입 → 대화 흐름 파괴
3. **인라인 blockquote (채택)**: 부모 아래에 스레드 전체를 묶어서 표시

### 이유

LLM이 "이 스레드의 결론이 뭐야?"를 분석하려면 스레드의 전체 맥락이 하나의 블록에 있어야 한다. 인라인 blockquote는 QMD 청킹에서도 하나의 의미 단위로 묶일 가능성이 높다.
